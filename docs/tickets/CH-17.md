# CH-17: Git hooks that rebuild the board

## Status

in progress (2026-11-23), Milestone B

## Depends on

CH-16

## Scope

The board rebuilds itself when ticket state changes. These hooks run on other people's machines, so the ticket is high-risk.

- **Hooks:** `post-checkout` (runs on `git worktree add` and switches), `post-commit`, `post-merge`, `post-rewrite` (amend, rebase, cherry-pick). Each one:
  - runs `dev-harness-board` quietly;
  - skips the rebuild unless a tracker or ticket file changed, or (for post-checkout) a worktree was added;
  - **never fails the git command:** exit 0 always, errors go to stderr as one line;
  - has a time limit (a few seconds);
  - writes into the main checkout's board (CH-16).
- **Chaining existing hooks:** setting `core.hooksPath` replaces `.git/hooks`. So each hook first runs the repo's own hook of the same name, if it exists and is executable (e.g. Git LFS's `post-checkout`, `post-commit`, `post-merge`), with the same arguments and stdin, and passes on its exit code where git cares.
  - Also add pass-through hooks for every hook name the repo already had in `.git/hooks` (e.g. LFS's `pre-push`), so nothing is lost.
- **Installer:** `dev-harness-board install-hooks`:
  - writes the hook files into a tracked folder (`.githooks/` by default; a setting can change it);
  - sets `core.hooksPath` only once that folder exists on the integration branch;
  - refuses if `core.hooksPath` already points somewhere else, and says what to do;
  - `--check` reports what it would change and writes nothing.
  - `uninstall-hooks` unsets `core.hooksPath` only if it points at our folder.
- **Owner decision (2026-11-23, review round 1), replacing the tracked folder above:** the hooks live in an untracked folder inside the git common dir, `<git-common-dir>/dev-harness/hooks`, and `core.hooksPath` is set to its absolute path. Nothing is committed (no "commit first" step, no `--dir`); each clone opts in by running `install-hooks`. `install-hooks --check` and the board's `--check` warn when a local `core.hooksPath` names a dev-harness folder that no longer exists (for example after the repo moved); rerunning the installer repairs it. Chaining still runs `<common-dir>/hooks/<name>`.
- **Guard interplay:** CH-04 asks before shell commands that change `core.hooksPath`. The installer is run by the owner (or asks, as normal); don't add exceptions to the guard.

Don't: change global or system git config; overwrite a hook file someone else wrote; touch `.git/hooks`.

## Done criteria

- Real-git tests in temp repos:
  - commit, amend, cherry-pick, rebase and `worktree add` each rebuild the board in the main checkout;
  - a commit touching no ticket files doesn't rebuild;
  - a failing or slow board build doesn't fail or noticeably block the commit;
  - an existing executable `.git/hooks/post-commit` and `pre-push` still run, with the right arguments and stdin;
  - the installer refuses a foreign `core.hooksPath`;
  - `--check` writes nothing;
  - `uninstall-hooks` leaves foreign settings alone.
- A test with a fake `git-lfs` hook proves LFS hooks keep running.
- Mutation checks:
  - drop the chaining, and a test fails;
  - drop the always-exit-0, and a test fails.
- Full suite and static check pass. Review rounds: at most 2.

## Follow-ups

- The CH-04 guard asks before shell commands that change `core.hooksPath`, but not before `dev-harness-board install-hooks` / `uninstall-hooks`, which change it through their own `git config` call. Owner to decide whether the guard should ask for those too (a project can add them to `askCommands` meanwhile).
- Hooks added to `.git/hooks` after install are not run until `install-hooks` is run again.
- The recursion marker also skips a same-named hook of the same repository for a git command run inside the chained hook (for example a `post-checkout` that runs `git checkout`); other repositories are not affected.
- Amend runs both `post-commit` and `post-rewrite`, so the board is rebuilt twice; a range cherry-pick rebuilds once per commit.
- `uninstall-hooks` leaves the scripts in `.git/dev-harness/hooks` (unused); no command deletes them.
