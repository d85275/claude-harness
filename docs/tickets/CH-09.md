# CH-09: Push policy that lets agents push feature branches, never `main`

## Status

parked (2026-11-23) after three high-risk review rounds, as the owner agreed before round 3. The work is kept on `feature/ch-09` (commit 21c2d14, base 7dc60ed, worktree `.worktrees/ch-09`), not integrated. Pushes stay on `"ask"` for 1.0.

## Depends on

## Scope

**Owner decision 2026-11-23:** agents may push feature branches to the remote without a prompt, but never `main`/`master`. The same rule applies to the main session and to subagents.

A new `pushPolicy` value, `"feature-branches"`. A push runs without a prompt only when the guard can prove that every target is a feature branch. Anything it can't prove asks.

- **Feature branch:** a branch matching `featureBranchPatterns` in `harness.json` (new key; default `["feature/*"]`). The integration branch (`tickets.integrationBranch`), `main` and `master` are never feature branches, whatever the pattern says.
- **Strictness order for the merge:** `deny` > `ask` > `feature-branches` > `allow` (configs merge and are never weaker, CH-01).

### Must pass without a prompt (policy `feature-branches`)

- `git push origin feature/ch-05`
- `git push -u origin feature/ch-05`, `--set-upstream`
- `git push origin feature/ch-05:feature/ch-05`, `refs/heads/feature/x:refs/heads/feature/x`
- several refspecs that are all feature branches
- `git -C <dir> push origin feature/x`
- the remote is a named remote that exists in that repo (`git remote` lookup, 2 s timeout; failure asks)

### Must ask

- `main`, `master`, the integration branch, as source-only or as destination: `git push origin main`, `HEAD:main`, `feature/x:main`, `refs/heads/main`
- a target that depends on git settings: plain `git push`, `git push origin`, `git push origin HEAD`, `git push origin @`
- force or history overwrite: `--force`, `-f`, `--force-with-lease`, `--force-if-includes`, a `+` refspec
- deletes and bulk pushes: `--delete`, `-d`, `:feature/x`, `--all`, `--mirror`, `--tags`, `--follow-tags`, `--prune`
- a URL or path as the remote, or an unknown remote name
- tags as a refspec (`refs/tags/...`, `v1.0.0`) or any refspec not under `refs/heads/` once qualified
- options the guard does not know
- every form the CH-03 detector already treats as a push (`sh -c`, `eval`, aliases it detects, `--exec`/`-c` tricks): if any push in the command fails the proof, the whole command asks
- `gh pr create`/merge and deploy commands keep their current ask

### Policies `ask`, `deny`, `allow`

Unchanged; the CH-03 corpus rows for them must pass as they are.

## Findings

- **Round 1** (d3d15c7): CHANGES REQUIRED. Real pushes to `main` on a local bare remote, using:
  - `push.default=upstream`/`tracking`;
  - a feature branch that is a symbolic ref to `main`;
  - `checkout`/`switch` in the same line turning on `includeIf onbranch` config.

  Minor: pushurl/insteadOf, recurseSubmodules, time budget, `tag` keyword, integrationBranch normalisation. All fixed in 9ea0b88.
- **Round 2** (9ea0b88): CHANGES REQUIRED.
  - Critical: `git log`/`show`/`diff --output=<file>` in the same line rewrote `.git/config` or a branch file before the push, and `main` moved.
  - Important: `push.pushOption` was not checked.

  Fixed in 21c2d14: a push line may also run only `echo`, `true`, `pwd`, `git add` and `git commit`; `push.pushOption` asks; remote names keep their case.
- **Round 3** (21c2d14, extra round approved by the owner): CHANGES REQUIRED.
  - Round-2 repros all ask now.
  - New bypass: an earlier, separately allowed `git symbolic-ref HEAD refs/tags/feature/x` in a linked worktree; then `git -C ../wt commit --allow-empty -m x && git push origin feature/x`. The commit creates the tag after the proof ran, and the push creates `refs/tags/feature/x` on the remote without a prompt. It never reaches `main`. Repro: reviewer scratch script `ch09-r3/bin/h3.sh` case H11; variant `refs/feature/x` (h2.sh H9b).
  - Suggested fix: for each `git [-C dir] commit` in a push line, ask unless `git [-C dir] symbolic-ref -q HEAD` is empty or under `refs/heads/`.
  - Minor: `commit -n` and `--no-veri` skip hooks but aren't refused; pre-installed hooks, filters and fsmonitor are trusted (could push on their own anyway).
