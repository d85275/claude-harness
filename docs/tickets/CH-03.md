# CH-03: Push policy ("nothing leaves your machine without your approval")

## Status

planned (2026-11-22)

## Depends on

CH-01

## Scope

`guard.py` always asks before `git push`, `gh pr create/merge`, `gh repo create/delete` and `gh release create`. This ticket makes that behaviour a setting, `pushPolicy`:

- `"ask"` (default): the owner approves each one.
- `"deny"`: blocked outright, with a message saying the owner pushes by hand.
- `"allow"`: no prompt from this hook. The user's own Claude Code permission rules still apply. Documented as meant for the owner's interactive sessions; agents still never push.

Owner decision 2026-11-22: `pushPolicy` covers only git/GitHub publishing. Deploys and destructive cloud commands (`firebase deploy`, `gcloud … deploy/delete`, `terraform apply/destroy`, `kubectl apply/delete`, `askCommands`) always ask, whatever the policy.

Don't: change the credential or weakening guards.

## Done criteria

- Tests for each policy against `git push`, `git -C dir push`, `git -c x=y push`, `gh pr create`, `gh pr merge`, plus a deploy command that still asks under `"allow"`.
- One test pins the default as `"ask"` when no config exists.
- README states "nothing leaves your machine without your approval" and documents the three values.

## Allowed files

`hooks/scripts/guard.py`, `tests/`, `README.md`, `templates/harness.json`

## Review level

high-risk (security enforcement: this guard is the main promise of the plugin)

## Findings

- Implementation found that `"allow"` adds a bypass: the Edit/Write guard asks on `.claude/harness.json`, but a Bash write such as `echo '{"pushPolicy":"allow"}' > .claude/harness.json` was unguarded, and the next `git push` would then pass this hook without a prompt.
- Owner decisions 2026-11-22:
  1. Keep `"allow"`, and guard shell writes to protected configs (`DEFAULT_PROTECTED_CONFIGS` + `protectedConfigs`, matched relative to the working directory and every loaded project root). They ask, never block. Order: the credential block first, then pushPolicy (`"deny"` blocks a push first), then this ask with the other ask checks. The README states that common shell writes are caught, not all, and that permission deny rules are the hard boundary.
  2. Keep the stricter push detection: a word check after shell parsing alongside the regex, catching quoted words, quoted `-c` values, `GIT`/`Git` and `git-push`.
  3. Subagents: no change in this ticket. `"allow"` also applies to subagents (README says so); the coordinator files the subagent question as a follow-up.
- High-risk review round 1 (2026-11-22), changes required; resolved in the same commit:
  1. [Critical] Cost: `eval` recursion was combinatorial (92 "eval" words in 1.6 KB took 21-25 s; a timed-out PreToolUse hook does not block, so a slow guard fails open). Now `eval` recurses once per segment, inputs are deduplicated, and the whole Bash check runs inside a work budget (`CHECK_SECONDS` 1.5 s, `CHECK_STEPS`, and `LONGEST_WORD` 32 KB because shlex is quadratic in one word's length). Over budget it asks "command too large to check; approve manually", never allows or blocks.
  2. [Important] Matching cost: candidates are deduplicated and prefiltered on their last path part before `fnmatch`. The backtracking option loop in the publish regexes now needs option values that do not start with `-`. The deploy rule for `gcloud` pins the first `gcloud` on a line with a lookahead, so it runs in linear time. The coarse raw-text writer regex is gone (see 6).
  3. [Important] Publish bypasses now caught: `gh pr/release/repo new`, `gh gist create/new`, `gh -R/--repo/--hostname X ...`, backslash-newline continuations, `#` comments with an apostrophe (comments are stripped at word start, outside quotes; shlex's own comment handling ate mid-word `#`), `git $'push'`.
  4. [Important] Config-write bypasses now caught: folders (`cp x .claude/`, `cp -t .claude x`, `rsync -a dir/ .claude/`, `rm -rf .claude`, `rm -rf .`), globs (`.claude/*.json`, `.claude/*`, `harness.js?n`), and a `cd`/`pushd`/`git -C` earlier in the same command. On macOS, config paths match in any letter case.
  5. [Approved addition] Under `"allow"`, a detected publish runs one `git status --porcelain --ignored --untracked-files=all` (3 s timeout) on every `harness.json` in the repository and every loaded one. Modified, staged, deleted, untracked or ignored, or a git error, asks: "push policy file changed in the working tree".
  6. [Minor] Noise: work is per simple command; `tee` and `cp` targets are their own arguments; interpreters count only `-c`/`-e` code, heredoc bodies and here-strings; data heredocs (`git commit -F -`, `cat > f <<EOF`) are not read as commands; `git restore --staged` is index-only. Of the reviewer's 11 noisy everyday commands, 10 now pass. `python3 -c "...json.load(open('.claude/harness.json'))"` still asks, because the guard cannot tell a read from a write in code text.
  7. [Minor] Errors in the push or config check ask; a NUL byte in the command asks (bash stops reading at a NUL, so the text is not what would run).
  8. [Minor] README lists the undetected publish paths and states the reads that pass.
- High-risk review round 2 (2026-11-22), changes required; resolved in the same commit:
  1. [Critical] Three regressions, one cause: the scanner deleted text (comments, heredoc bodies) and the checks read only what was left, so a parse mistake failed open. `git commit -m "$(echo "Closes #12")" && git push` (a nested quote made `#12...` a comment), a heredoc piped to a shell (`cat <<'EOF' | bash` with `git push` in the body; also `sh -s`, `xargs rm`, `python3`, `source /dev/stdin`), and `x=$((1<<2))` (arithmetic `<<` opened a fake heredoc). Structural rule now: the publish and redirect regexes read the full text (only backslash-newlines joined); a hit is dropped only inside the body of a plain data heredoc (`git commit -F -`, `git tag -F -`, `cat > file`, `cat >> file`, `tee file`; one heredoc on the line, no pipe, backtick, `$(`, process substitution or `&`; delimiter found; quoted delimiter or no `$`/backtick in the body). Every other heredoc body is checked as commands. Comments are stripped only on lines without `$(`, backticks or `((`. No heredocs inside `$((...))`/`((...))`.
  2. [Minor] Publish option loops are limited to 8 options; commands over 256 KB ask as too large.
  3. [Minor] A recursive `cp`/`rsync`/`ditto` into a folder that holds a protected config counts (`cp -R src/. .`).
  4. [Minor] `cd -P`/`cd --` options are skipped; each `cd` adds one folder (no doubling), so six `cd`s no longer ask.
  5. [Minor] The allow check runs `git --no-optional-locks status` and then `git ls-files -v` (assume-unchanged or skip-worktree entries ask), within 3 s; `git update-index` on a protected config asks.
  6. [Minor] Test for `git -C .claude/hooks checkout ../settings.json`; cost tests measure CPU time.
  7. Regression corpus: `tests/data/guard_corpus.txt` (214 made-up commands from both review rounds, expected decision for none/ask/deny/allow), run by `tests/test_guard_corpus.py`. Known gaps are rows marked `# gap:`.
- High-risk review round 3 (2026-11-22): every round-2 item confirmed fixed; the corpus catches regressions (89 failures on 94d6c47, 481 on main). Owner decision 2026-11-22: small fix, the coordinator verifies, then close; no 4th review round. Fixed in the same commit:
  1. [Important] A script written by a data heredoc and run later in the same command was never checked (main asked). A `cat >`, `cat >>` or `tee` heredoc now counts as data only when the rest of the command does not name its file again (same path without `./`, or the same file name when either side is relative); otherwise the scan repeats with that body checked as commands. Corpus rows: `bash`, `chmod +x && ./file`, `source`, `python3` on the written file, `sh run.sh` after `cat >> ./run.sh` (deny blocks), the config variant (asks), and a plain `cat > notes.md` heredoc mentioning git push that stays allowed under deny.
  2. [Minor] Corpus rows that kill mutation survivor S1 (regexes reading the scanned text): `echo "${x:-"a # b"}"; git push` and a multi-line `x="$(echo "a` / `# b")"; git push origin HEAD`, both deny=block. README corrected on comment stripping: quotes nested inside `${...}` or a multi-line `$(...)` can be misread; publishing is still caught by the full-text regexes, and the matching config-write case is a known gap (corpus row marked `# gap:`).
- Process note (round 1): the installed plugin's credential guard blocked one of the implementer's Bash commands because the test text it carried contained `cat .env`; the implementer applied the same edit through a scratchpad script instead of stopping to report. The reviewer confirmed nothing read a credential. Rule from the coordinator: when a guard blocks a command, stop and report it.
- Follow-ups only (not fixed here):
  - Older fail-open: when `guard.py` crashes, `main()` exits 0 and the call runs unchecked (every guard, push included). This includes a malformed hook payload (`"command"` not a string, `"tool_input"` not an object), which crashes before the new checks.
  - Publishing paths not detected: `git lfs push`, `git subtree push`, `git send-pack`, git aliases for push (`git -c alias.p=push p`), `gh api` calls that create PRs or releases, and commands built from shell variables.
  - Config writes not detected: `tar`, `patch`, `git apply`, `git stash pop`, formatters such as `prettier --write`, `python3 -m json.tool IN OUT`, a write hidden behind a comment misread inside `${...}` or a multi-line `$(...)`, paths built from variables, scripts run from separate files.
  - Owner decision: credential check cost (older code, out of this ticket's scope; it runs before the new checks). On main (d47db42) a 1 MB single-word command takes 22 s CPU and a 1 MB `python3 -` heredoc 6 s, past the 10 s hook timeout, which does not block: a fail-open. A size check ahead of it would change the credential guard, which this ticket may not do. Details: it runs `matches()` on every word when a read verb such as `sed` or `python3` appears, about 0.4-0.5 s for 50-100 KB commands, and its own `shlex.split` is quadratic in one word's length (about 0.8 s for a 200 KB word).
