# CH-31: A wildcard write asks only when it can reach a protected config

## Status

in review (2026-11-24): owner request after a false prompt in a real project

## Depends on

none

## Scope

A shell command that deletes or writes files through a wildcard (`rm -f app/build/test-results/testDebugUnitTest/*.xml`) asks the owner, because `ConfigMatcher.hit` (`hooks/scripts/shell_check.py`) treats a glob as a hit when it could match a protected config by name (`*.xml` could be `**/lint.xml`). In a build output folder this is a false prompt. The prompt also shows only the first 200 characters of the command, so the owner cannot see which part triggered it.

- **Look at the real files.** When a written word is a glob, expand it against the file system the way the shell would, relative to the command's working directory (including a `cd` earlier in the same command, if the checker already tracks it; otherwise the hook's cwd). Ask only if one of the expanded paths is a protected config (by the existing rules), or a protected config could appear there. Let it through when the expansion is known and none is protected.
- **Fail closed.** Keep today's behaviour (ask) whenever the expansion is not certain, for example: the glob is in a folder outside every project root and the cwd; it contains variables, `~`, command substitution, brace expansion or `**`; the folder cannot be read; an earlier part of the same command could create or rename files in that folder (any write, move, copy, archive extraction, build or unknown command before it in the chain, with the target folder unknown); the expansion is too large (keep a small cap and ask past it). When unsure, ask.
- **Better prompt.** The message names the command word and the protected pattern that matched, and quotes the part of the command that triggered it (for example `rm -f …/*.xml could match **/lint.xml`), not only the first 200 characters.
- Edit/Write tool calls and non-glob paths are unchanged.

Don't: drop or narrow any protected pattern; change credential, push, deploy or hooks-folder rules; let a glob through on a name-only argument.

## Done criteria

- Tests with a temp project: `rm -f build/out/*.xml` with no protected file in that folder passes; the same with a `lint.xml` in that folder asks; a glob in a folder holding `.claude/harness.json`-like matches asks; each fail-closed case above asks (one test each, at least: variable in the path, `**`, brace, unreadable folder, a write earlier in the chain into the same folder, outside the roots, over the cap).
- The new pass test fails without the change; all existing guard tests and the guard corpus pass unchanged (or each change is explained in Findings).
- The prompt text names the verb and the matched pattern; a test checks it.
- `docs/guards.md` describes the rule and its limits.
- Full suite and static check pass. Review rounds: at most 3.

## Allowed files

`hooks/scripts/shell_check.py`, `hooks/scripts/bash_rules.py`, `hooks/scripts/guard.py` (only the prompt text), `tests/`, `docs/guards.md`

## Review level

high-risk (it narrows when a guard asks)

## Findings

- **Owner decisions (2026-11-25), review round 1.** (1) Other commands in the line: the guard protects the configs that exist when the command starts, and the folder listing sees exactly those, so an unrelated command (a build, a test run, `echo $?`, `grep`, a pipe to `head`) no longer stops the expansion. It still asks when another command could put files into, or rename files in, the glob's folder or a parent of it, when another command's target cannot be read, and in every earlier fail-closed case (implemented with allow-lists since round 2, below). (2) `cd app` (plain relative name) is followed when `CDPATH` is unset or empty in the hook's environment; when it is set, or the command sets it, it asks.
- **The reported command now passes** when `app/build/test-results/testDebugUnitTest/` holds no protected config (`./gradlew testDebugUnitTest assembleDebug > /tmp/x.log 2>&1; echo $?; rm -f .../*.xml`), and asks with a `lint.xml` there: ``rm: `rm -f app/build/test-results/testDebugUnitTest/*.xml` reaches app/build/test-results/testDebugUnitTest/lint.xml, which matches **/lint.xml``. Both are tests.
- **Review round 2 (high-risk review of 189ffed, 5 findings with repros, each deleting or moving `app/lint.xml`): deny-lists replaced by allow-lists** (coordinator direction). Round 1 classified other commands by deny-lists, which missed `cd` after a keyword or prefix (`if ...; then cd app; fi`, `{ cd app; }`, `X=1 cd app`, `time cd app`, `! cd app`), runners such as `git -c core.fsmonitor=...`, `awk system()`, `sed 1e`, `env -S`, `watch`, `fish -c`, option-attached targets (`mv -tbuild/out app`), `..` after a wildcard, and quoted `C""DPATH`. Now (`ShellCheck.glob_changes`, `effect`, `readable_command`):
  - **Shape:** the line must be a flat list of simple commands joined by `;`, `&&`, `||`, `|` or newlines, plus redirections; any other operator token (`(`, `)`, `&`, `|&`, ...) asks, nested shell text (`sh -c`, `eval`) asks, and any heredoc whose body is read as commands asks. Keywords, `{`, `!`, `time`, `[[`, `coproc` and `NAME=` prefixes ask because no other command's first word may be anything but an allow-listed word.
  - **Other commands:** exact first word on the allow-lists in `docs/guards.md` (readers and removers; build and test runners without `-c`/`-e`/`--eval`/`--exec`/`-exec`/`--command`; `npm`/`pnpm`/`yarn`/`swift`/`cargo`/`go` with a listed subcommand first; `python3 -m unittest|pytest`; `git` read subcommands right after `git`, so no `-c`, `-C` or `--config-env`, and no `--output`/`-O`/`--open-files-in-pager`). `rm`, `rmdir`, `unlink` are on the reader list because they only remove (not in the coordinator's suggested list; they cannot put or rename files). Everything else asks, including every placing command (`cp`, `mv`, `ln`, `install`, `rsync`, `tee`, `tar`, `unzip`, ...), so option spellings no longer matter.
  - **`cd`:** only as the first word with one plain argument; `cd -`, `cd +N`/`-N`, bare `cd`, `..`, variables, `pushd`, `popd` ask; a `cd` into a missing folder asks.
  - **`..`** anywhere in the glob word asks.
  - **CDPATH:** any `cdpath` in the text after removing quotes and backslashes, in any case, asks (plus `CDPATH` set in the hook's environment with a plain `cd`). `export`, `declare`, `read`, `printf -v` and the rest are not allow-listed, so they ask anyway.
  - **Redirects** of allowed commands are the only remaining path comparison (`bash_rules.folder_changed`): a target in the glob's folder, inside it or a parent of it, or an unreadable target, asks.
  - **Base rule unchanged:** outside this path, a glob asks by name as before; `docs/guards.md` now says so.
- **Review round 3 (of 3) on b54870a: changes required; all 30 round-2 repros held.** Findings: build runners took any option (`make -f -` from a pipe or here-string, `go build -toolexec=...`, ran for real; also `make -f /dev/stdin`, `make -E'...'`, `make --eva=...`, `go test -toolexec=...`, `cargo test --config '...runner...'`); git reads accepted shortened long options (`git grep --open=...` ran for real; `--open-files-in=...`, `git diff --outp=...`); `uniq - out` did not count `-` as a file.
- **Review round 4 (owner-approved extra round, 2026-11-25): the owner's strict rule** (`ShellCheck.readable_command`, `stdin_flags`). Build and test runners and git reads count only with plain arguments: every word after the runner matches `^[A-Za-z0-9_:.,/+@-]+$`, none is `-`, `/dev/...` or `/proc/...`, the runner does not read stdin (not after a `|`, no `<`, `<<`, `<<<`), and a word starting with `-` must be on the runner's exact option list (`BUILDER_OPTIONS`, `BUILDER_SUBCOMMANDS`, `PYTHON_MODULES`, `GIT_OPTIONS`, plus `-jN` for make and `-N`/`-nN` for git). Exact lists rather than prefix bans, so shortened long options cannot slip through. `uniq` counts `-` as a file. The redirect of the reported gradlew command belongs to the line, not to a runner argument, so it still passes. Stricter side effects (intended): `git show HEAD~1`, `git log --format=...`, `./gradlew --console=plain`, `make FOO=bar`, `cat x | ./gradlew build` and `./gradlew build < /dev/null` ask.
- **Recheck of 654b3cf: one more allow path closed (tightening only).** Plain arguments to `npm`/`pnpm`/`yarn` `install` linked a folder or fetched a package (`npm install ./app` created `node_modules/app -> ../app`, run for real by the reviewer with npm 10.9.2), and `yarn run` / `pnpm run` fall back to any installed CLI (`yarn run shx mv app build/out`). Now `install`, `ci` and `i` count only with no word after them (`INSTALL_SUBCOMMANDS`), and `run` is listed for `npm` only; `npm test` and `npm run <name>` are unchanged. `docs/guards.md` adds the limit that settings persisting in a tool's own config (`go env -w GOFLAGS=...`, `npm config set script-shell ...`, `.cargo/config.toml`) can carry code into a later listed build.
- **Accepted limit (owner decision).** A file that an allow-listed build or test runner, or another process, creates in or moves into the folder before the glob runs is not seen; the runner's own project files (`build.gradle`, `Makefile`, `package.json` scripts, `.cargo/config.toml`, `conftest.py`) decide what it runs. The repository's own git config (`core.fsmonitor`, `diff.external`, `*.textconv`, `filter.*`, `core.pager`) runs during the git reads. Documented in `docs/guards.md`.
- **Still asking:** a glob after `do`, `then` or `{` (the keyword is the first word); subshells `( ... )` and background `&` (round 1 let these pass).
- **Which globs are expanded.** Only a glob given to `rm`, `unlink`, `cp`, `mv`, `ln`, `install`, `touch`, `truncate`, `chmod`, `chown`, `chgrp` as the first word (exact spelling), since their arguments are plain names (a quoted or unmatched glob reaches them literally, and the literal name is checked too). Everywhere else (`find -name`, `sed -i`, `rsync`, redirects, `tee`, `xargs`, `sudo`, `bash -c`, `eval`, interpreter code) the old name rule stays.
- **Superset listing.** Dot files, `.`/`..` and any letter case match; matched folders are walked (so `rm -rf build/*` asks for a `lint.xml` anywhere under `build/`); real paths are checked as well as the written ones. It also asks for: a listed folder that is itself on the way to a protected config (`.claude/*`, even when empty), more than 200 paths, more than 5000 entries in a folder, a matched name with glob characters, a leading `-` (option injection), `.`/`..`, a link to a folder, a file with other hard links, a folder outside the cwd and project roots, an unreadable folder. A folder that does not exist matches nothing and passes (the literal name is checked).
- **Pre-existing gap fixed on the way (asks more).** Brace words were never name-matched, so `rm .claude/{harness,x}.json` and `rm -f build/out/{l,x}*.xml` passed on `main`. A `{a,b}`/`{1..9}` group is now read as `*` for name matching, and a brace glob always asks. Shown by running the new tests on the base tree (the brace rows are `allow` on base; see the base run in Evidence).
- **Architecture kept.** `shell_check.py` stays I/O-free (its `test_shell_check_has_no_io_and_no_exit` test is unchanged): ShellCheck defers the candidate globs and decides the pure "may change" part; `bash_rules.expand_globs` lists the folders inside the same work budget and `try` (an error or budget overrun asks).
- **Prompt.** `ConfigMatcher.hit` now returns the matched pattern; the prompt names the command word, the quoted part of the command and the pattern (`reaches <path>, which matches <pattern>` / `could match <pattern> (<reason>)` / `matches <pattern>`), then the first 200 characters of the command as before. `guard.py` was not changed (the text is built in `bash_rules.py`).
- No existing test, corpus row or threshold was changed.

## Follow-ups

Not new on base (reviewer, round 2), left as they are:

- `rm -rf app`, `chmod -R` or `mv` of a folder that holds a config counts only by the folder's name, so it passes when the name is not a config's.
- `{ cd .claude; }; ...` with a relative write after it: the `cd` is not followed by the name rule (the glob path is now covered by the shape rule).
- A hard link to a config under another name is not matched by name (a glob that reaches one now asks).
- A folder that is a symbolic link to a config folder (`cfg -> .claude`) is not followed for non-glob words or for globs that cannot match by name (`rm cfg/settings.json`, `rm -f cfg/*.json` pass, as on `main`); `chmod 644 cfg/*` now asks.
- zsh alternation `rm (lint|x).xml` is split at `|` into two commands by the scanner, so it is not matched (as on `main`).
- An option-attached destination in a write (`mv -t.claude x`) is skipped by the name rule as an option (as on `main`).
- Reviewer suggestion (round 3): ask before `git config` writes `core.fsmonitor`, `diff.external`, `*.textconv`, `filter.*` or `core.pager` (they make later git reads run commands; today only `core.hooksPath` asks).
